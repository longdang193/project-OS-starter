# Project Charter

## Problem

This starter exists to make project purpose, repo method, structured lifecycle
meaning and execution work separable from the beginning.

A new project should not have to invent its planning system, documentation
ownership model, and private/public governance from scratch while also trying to
ship product code.

## Project Shape

This starter combines four goals that should stay aligned:

- a stable intent layer that explains what the project is for
- an operating-system layer that explains how the repo should build and govern work
- executable truth in code, configuration, schemas, and tests
- execution artifact layers for specs and plans that do not replace executable truth

## Core Promises

The starter should preserve these promises:

- README remains synthesized rather than becoming the deepest source of truth
- project intent remains distinct from repo method
- generated docs remain generated rather than hand-maintained forks
- specs and plans remain execution artifacts rather than replacing executable truth
- private/public repo boundaries remain explicit when a project needs both surfaces

## Why This Starter Exists

This starter should help future projects do three things well:

- begin with a clean source-of-truth model
- evolve product behavior and governance without accidental duplication
- reuse disciplined patterns without copying one specific product architecture wholesale
